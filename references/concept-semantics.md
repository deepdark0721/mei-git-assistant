# 概念与语义辨析

> 本文件承载 Git 的深层概念与命令语义辨析，回答"这条命令到底做了什么、和另一条有什么本质区别"。
> 命令速查见 `git-commands.md`，IDE 操作对照见 `clion-ide-mapping.md`。
> 来源：飞书文档《更适合SRM宝宝的Clion-Git教程》，整理于 2026-08。

## 一、核心概念：先把心智模型摆正

### 1. HEAD 指向分支，不指向提交

- 每次提交把一串提交串成一条时间线，这条时间线就是一个分支。
- 分支指针（如 `master`）指向具体的提交；**HEAD 指向当前分支**，不直接指向提交。
- 切换分支时 HEAD 改指向另一个分支指针；新建分支只是复制一个指针指向同一提交，再把 HEAD 切过去。

### 2. 三层存储模型

| 层 | 位置 | 内容 |
|----|------|------|
| 工作区 | 普通文件夹 | 你正在编辑的文件 |
| 暂存区（stage / index） | `.git` 内部 | 选中的待提交内容 |
| 版本库 | `.git` 内部 | 每个文件的修改、删除记录，可随时还原 |

- `.git` 目录属于版本库，不属于工作区。
- 流程固定：工作区修改 → `git add` 进暂存区 → `git commit` 落到当前分支。

### 3. Git 管理的是修改，不是文件快照

- Git 跟踪的是"哪几行被改了"，不是每个版本的整文件。
- 后果：直接签出旧提交且本地有不冲突的未提交修改时，切换能成功，但修改会被"带过去"，污染目标状态。
- 暂存区的最小单位是**块（hunk，连续修改的行）**：同一 hunk 的新暂存会覆盖旧暂存，只保留最终结果快照。

## 二、detached HEAD（游离头指针）

### 是什么

`git checkout <commit>` 会让 HEAD 直接指向某个具体提交，而不是某个分支——此时处于 **detached HEAD** 状态，即只读历史状态。

```bash
git checkout <commit>    # 进入 detached HEAD
```

### 为什么不能提交

此时提交不属于任何一个分支，提交完就"无家可归"，reflog 之外再难找回。因此认为它是只读状态。

### 退出 / 修复路径

```bash
git switch -c <new-branch>    # 基于该提交开新分支，继续工作
git switch <branch>           # 或直接切回已有分支
```

### 常见坑

- 有已修改而未提交的文件时直接签出旧提交：
  - 冲突的修改：切换直接报错，未提交修改不会消失但被拦住。
  - 不冲突的修改：能切换成功，但修改会污染目标文件（见上文"Git 管理的是修改"）。

## 三、撤销的三层心智模型

按"改动是否已提交、是否已推送"选择层级，不要乱用。

### 层级 1：撤销未提交的工作区修改 —— `git restore`

```bash
git restore <file>            # 丢弃工作区修改，回到上次提交
git restore --staged <file>   # 把文件移出暂存区（取消 stage）
```

### 层级 2：撤销上一次提交（未推送）—— `git reset --soft`

- 仅适用于刚提交、未推送的场景。
- 前提：目标分支不是受保护分支（受保护分支不允许 force push）。
- 撤销提交但保留更改，可重新组织后再提交。

```bash
git reset --soft HEAD~1    # 撤销提交，更改保留在工作区
```

### 层级 3：安全撤销已推送的提交 —— `git revert`

- **不删除、不改写历史**，而是创建一个新提交，抵消目标提交的变更。
- 基于当前 HEAD 所指向的状态做抵消。

```bash
git revert <commit>
```

### revert 冲突的完整机制

revert 也可能冲突。典型例子：三次提交改同一行。

- 提交 A：把 `x` 从 1 改成 10（你要 revert 的）。
- 提交 B：再把 `x` 改成 20（当前 HEAD）。
- revert A 时 Git 想把 10 变回 1，但当前代码是 20，Git 不知道应回到 1 还是保留 20 → 冲突。

冲突发生后的结果：

1. `git revert` 进程暂停。
2. 工作区文件被标记为冲突状态。
3. 不会自动创建 revert 提交。
4. 需手动解决冲突。
5. 解决后手动 `git add` + `git commit` 完成 revert。

## 四、语义辨析四组

### 1. merge vs rebase：历史形态不同

| 维度 | merge | rebase |
|------|-------|--------|
| 历史形态 | 保留交汇点，产生合并提交（多父项） | 把提交"搬移重放"，历史变线性 |
| 语义 | 把分支合并进来，记录"何时合并" | 把分支提交重放到目标之上 |
| 适用 | 保留合并痕迹、团队协作 | 整理本地提交、保持主线干净 |

```bash
git merge <branch>          # 合并提交，有交汇点
git rebase <target>         # 提交重放，线性历史
```

rebase 之后本地历史与远端不一致，推送需 `--force-with-lease`。

### 2. fetch vs pull vs update（CLion）

| 操作 | 行为 |
|------|------|
| `git fetch origin` | 只把远端内容更新到本地远程跟踪分支 `origin/*`，本地其他分支不动 |
| `git pull` | 默认两件事：先 fetch 更新 `origin/*`，再把远端分支 merge 到本地当前分支 |
| `git pull --rebase` | fetch 之后用 rebase 代替 merge，本地提交重放到远端节点之后 |
| update（CLion，Ctrl+T） | 弹出两选项：合并到当前分支 / 在传入更改上变基当前分支；自动对应本地分支的远端分支（如 `branch1` 自动拉 `origin/branch1`） |

```bash
git fetch origin          # 只更新远程跟踪分支
git pull origin master    # fetch + merge
git pull --rebase         # fetch + rebase
```

### 3. squash vs fixup：整理历史的两种粒度

| 操作 | 效果 | 场景 |
|------|------|------|
| squash | 多个连续提交合并成一个，需输入新的提交信息 | 把一串琐碎提交整理成一次有意义提交 |
| fixup | 丢弃新提交的消息，只保留原始提交的消息，内容合并进去 | "悄悄"修复前面某次提交（typo、小 bug） |

```bash
git rebase -i <commit>^    # 把多个 pick 改为 squash，或把最新提交标为 fixup
```

fixup 前提：本地分支（未推送或可安全重写历史）；想合并的提交连续、位于 HEAD 之前；最新提交是刚做的"修复"提交。

### 4. 标签语义：轻量 vs 附注

| 类型 | 本质 | 用法 |
|------|------|------|
| 轻量标签 | 单纯指向提交的指针，可理解为提交哈希的别名 | 右键提交 → 新建标记，便于后续签出 |
| 附注标签 | Git 基本对象，蕴含 commit 哈希 + 元数据（作者、时间、注释） | 工具栏新建，可指定哈希或表达式 `<branch>~N` |

```bash
git tag <name>               # 轻量标签
git tag -a <name> -m "msg"   # 附注标签
git checkout <tag>           # 签出标签
```

**注意：标签只能被删除而不能被修改**，确保版本发布可靠、可追溯。

## 五、补丁（patch）

补丁记录**哪些行被添加、删除或修改了**。

```bash
git diff > change.patch    # 从未提交的修改生成补丁
git apply change.patch     # 应用补丁
```

三种使用方式：从未提交的更改创建补丁（存文件 / 复制剪贴板）；从已有文件创建补丁；应用补丁。
